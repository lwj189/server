## CP2（accept）

**1. 为什么 `accept` 第一个参数是 `server_fd`？**
因为 accept 是"从**监听 socket 的等位区**里取一个已完成握手的连接"。等位区是 `listen` 建在 `server_fd` 上的；`conn_fd` 是取出来的**结果**，它自己没有队列。
依据：`man 2 accept` —— "extracts the first connection request on the queue of pending connections for the **listening socket**"。

**2. `conn_fd` 和 `server_fd` 有什么区别？谁先关、谁后关？**
总机（`server_fd`，`listen` 后永久存在，只负责接待）vs 分机（`conn_fd`，一通电话一个）。
**`conn_fd` 先关**（处理完就关），**`server_fd` 最后关**（进程退出时）。反过来就再也接不了新连接。

**3. `client_len` 为什么每次都要重置？**
它是**值-结果参数**：传进去是"缓冲区有多大"，返回时被内核**改写**成"实际地址有多长"。下一轮不重置，传的就是上次的实际长度 → 内核会用错。

**4. `accept` 失败为什么用 `continue` 而不是 `return 1`？**
因为 accept 的失败**大多是暂时的**：`EINTR`（信号打断）、`ECONNABORTED`（客户端握手后又断了）、`EMFILE`/`ENFILE`（fd 用完）。这些不该让整个服务器退出。只有 `EINVAL`/`EBADF` 这类编程错误才该退。
依据：`man 2 accept` 的 ERRORS。

**5. 打印端口为什么要 `ntohs`？**
`sin_port` 存的是**网络字节序**（大端），`cout`/`printf` 按本机字节序（小端）读 → 不转会打成 20486 之类的怪数。
口诀：**填进去用 `hton*`，读出来用 `ntoh*`**。

## CP3（read）

**6. `read` 的三个返回值分别代表什么？**
`>0` = 读到的字节数；`0` = **EOF**（对端**正常**关闭）；`-1` = 出错，看 `errno`
（`EINTR` 重试 / `EAGAIN` 暂时没数据 / `ECONNRESET` 对端强断）。

**7. 为什么说"一次 `read` ≠ 一个请求"？man 里哪一句写过？**
`man 2 read` 的 NOTES：对 socket 这类对象，"if the requested number of bytes is not available, read() returns the bytes available" —— **可以少于你要的**。
本质：TCP 是字节流，**没有消息边界**。

**8. 一个连上但不发数据的客户端，为什么能卡死整个服务器？**
阻塞模型下 `read` **一直等**，唯一的服务线程就停在那一行。别的客户端连得上（内核的 accept 队列还能排），但**永远不会被 accept**。
这就是"阻塞的代价"，也是 epoll 的动机。

## CP4（send）

**9. `Content-Length` 填的是什么？填错了会怎样？**
填 **body 的字节数**（不含头部）。⚠ 是**字节数**不是字符数 —— 中文一个字 3 字节。
填小了：客户端会截断/粘包；填大了：客户端一直等剩下的，直到超时。

**10. `send` 第一个参数传谁？为什么不是 `server_fd`？**
传 **`conn_fd`**（分机）。数据要发给**某一条具体连接**；`server_fd` 是总机，它上面没有"数据通道"。

**11. `send` 的返回值为什么可能小于要求的长度？**
内核发送缓冲区满了。`send` 只保证"我**收下**了这么多"，不保证全收。
处理：循环发剩余部分，或者（非阻塞 + `EPOLLOUT`）挂输出缓冲。**CP6d 的活**。

**12. SIGPIPE 是什么？为什么忽略？不忽略会怎样？**
对端已关闭时再 `send`，内核给进程发 **SIGPIPE**，**默认动作是杀掉进程**。
`signal(SIGPIPE, SIG_IGN)` 之后，`send` 只是返回 `-1` + `errno=EPIPE`，可以正常处理。
**不忽略的话，一个恶劣客户端就能把你的服务器杀掉。**

## CP5a（半包）

**13. `read_buffer` 为什么必须声明在 `while (true)` 里面？**
那个 while 是"**每条连接**"的循环。放外面 = 所有客户端**共用一个缓冲区**，上一条的残留会污染下一条 → 表现为偶发的 400，**极难查**。
（epoll 版里它升级成了 `ClientContext::inbuf`，理由一样，只是"一条连接"的范围变了。）

**14. 判据为什么是 `\r\n\r\n` 而不是 `\n\n`？出自哪一节？**
**RFC 9112 §2.1**：HTTP 的行结束符是 **CRLF**；头部以一个**空行**结束 → 连着两个 CRLF。
而且 **body 里可能出现 `\n\n`**，用它会误判成头部结束。

**15. 超限检查为什么必须放在"找判据之后"？**
顺序反了会**误杀合法请求**：一个"头很小但 body 很大"的请求，缓冲区很快超过 `MAX_HEADER_SIZE`，但它完全正常。
**先看"收全没有"，再看"超限"。**

**16. 客户端一直发、永远不发判据，会怎样？你怎么防？**
`read_buffer` **无限增长** → 内存爆掉（DoS）。实测：没有上限时 RSS 从 4MB 涨到 14MB。
防法：`MAX_HEADER_SIZE`，超了就断开（更规范的是先回 **431** 再断）。

## CP5b（body）

**17. 为什么"头部收全了"不等于"请求收全了"？**
请求 = 头部 + **body**。`\r\n\r\n` 只标出**头部**的结尾；body 多长由 `Content-Length` 说了算，可能一字节都还没到。
头部收全只说明"**我知道 body 要多长了**"。

**18. 一个完整请求的总字节数怎么算？**
```
total = header_end + 4 + content_len
```
- `header_end` = `\r\n\r\n` 里**第一个 `\r` 的下标** = 头部**内容**的字节数
- `+4` = `\r\n\r\n` 这 4 个字节（头部内容**不含**它们）
- `content_len` = Content-Length 声明的 body 字节数（没有该字段按 **0**）
实测：`57 + 4 + 5 = 66` = 整个请求长度。

**19. 为什么用 `size() >= total` 而不是"再 read 一次 body 就到齐了"？**
因为一次 read **不保证**给你剩下的全部（返回值可能小于请求的长度）。
判据必须是"**缓冲区现有字节数 vs total**"，不能靠"读了几次"。

**20. `std::stoul` 遇到 `Content-Length: abc` 会怎样？不 catch 的后果？**
抛 `std::invalid_argument` → 不 catch 就穿出 main → **`std::terminate`，整个进程消失**（实测踩过）。
⚠ 注意：`stoul("10abc")` **不抛**，返回 **10**（解析到非数字就停）→ 所以要先 `isAllDigits`。

**21. 在 `while (true)` 里用 `continue` 之前，必须先做什么？为什么？**
**先把这条连接 `close` 掉**（epoll 版还要 `erase`）。
因为 `continue` 会**跳过循环末尾的清理代码**直接进下一轮 → 不关就是 fd 泄漏。

## HTTP / 定界

**22. 半包和粘包是同一个问题的两面吗？各需要什么手段？**
是同一个根因（**TCP 是字节流，没有边界**）的两面。
- **半包**（一个请求分多次到）→ **缓冲区 + 攒够再处理**
- **粘包**（多个请求挤在一次 read 里）→ **循环解析 + 消费已处理字节**
现在只解决了半包。

**23. 现在用什么方式"规避"粘包？代价是什么？**
回 `Connection: close` 然后关连接 —— 一条连接只服务一个请求，多余字节随连接丢弃。
代价：**没有 keep-alive**，每个请求都要重新握手；而且这是**规避**不是**解决**。

**24. 支持 keep-alive 要改哪三处？**
① **循环解析**：处理完一个请求后，`inbuf` 里还有就接着解析下一个（不能 `return true` 就走）
② **消费缓冲区**：`ctx.inbuf.erase(0, total)` 摘掉已处理的字节
③ **按请求决定关闭**：看 `Connection`（HTTP/1.1 默认 keep-alive，只有 `close` 才关）
＋配套 **idle 超时**（否则空连接永久占着）

## 解析的严谨性

**25. HTTP 头字段名区分大小写吗？哪一节？**
**不区分**。**RFC 9110 §5.1**："Field names are case-insensitive"。
`content-length` / `Content-Length` / `CONTENT-LENGTH` 是同一个字段。

**26. `Content-Length:5`（冒号后没空格）合法吗？语法出自哪节？**
**合法**。**RFC 9112 §5** 的 field-line 语法：
```
field-line = field-name ":" OWS field-value OWS
```
`OWS` = **0 个**或多个 SP/HTAB → 冒号后可以没有空格。

**27. `stoul("10abc")` 返回什么？为什么必须先 `isAllDigits`？**
返回 **10**（不报错）。RFC 9112 §6.3 要求无效的 Content-Length **必须以 400 拒绝**。
先卡成纯数字，剩下的 `stoull` 就只可能因**溢出**抛异常。

**28. 为什么"解析失败的测试"不能只看"最终有没有返回 200"？** 🔥
因为**提前响应**也会返回 200：body 还没到就回了 200，只看最后一眼会**漏掉**。
正确判据：**body 补齐之前服务器必须一个字节都不回**（等一小段确认 recv 超时），补齐后再要 200。
★ 这正是 t9/t11/t12 的设计 —— 也是这次抓到 `+ content_len` 漏写的那个判据。

## CP6a（epoll 事件循环）

**29. 为什么要把 `server_fd` 设成非阻塞？不设会怎样？**
事件循环里 accept 只是"顺手接一下"。阻塞的话，当 EPOLLIN 报上来但连接已被取走时，accept 会**挂起整个线程**。
非阻塞之后没连接就立刻 `-1 + EAGAIN` —— 这才有"**循环接到 EAGAIN**"这个写法。

**30. `fcntl(fd, F_GETFL, 0)` 里那个 `0` 是什么？为什么不能省？** ⚠
**题目前提错了：那个 `0` 可以省。**
实证：`man 2const F_GETFL` 的 SYNOPSIS 写的是
```c
int fcntl(int fd, F_GETFL);
```
**只有两个参数** —— F_GETFL 不需要第三个参数，写 `0` 只是习惯（fcntl 是可变参数函数）。
⚠ 别和 `F_SETFL` 混：**F_SETFL 的第三个参数才是关键**（要传标志位）。

**31. 为什么 `F_SETFL` 必须"读-改-写"三步？**
因为 `F_SETFL` 是**整体替换** file status flags，不是"或上去"。
直接 `F_SETFL, O_NONBLOCK` 会把已有的标志位（比如 `O_APPEND`）**抹掉**。实测踩过。

**32. `epoll_event.data.fd` 是谁填的？靠什么分辨事件属于哪个 fd？**
**你自己填的**（登记时写的），**不是内核给的** —— 内核只是**原样带回**。它就是个"你写给自己的标记"。
分流：`events[i].data.fd == server_fd`。

**33. `epoll_wait` 的三个返回值？`EINTR` 怎么处理？**
`>0` = 就绪 fd 个数；`0` = **超时**（不是错误；timeout=-1 时不会出现）；`-1` = 出错看 errno。
`EINTR` → `continue` **重试**（被信号打断，不是错误）；其它 → 报错退出。

**34. 为什么 `accept` 要循环到 `EAGAIN`？一次事件不是只对应一个连接吗？**
不是。一次 EPOLLIN 只表示"**至少有一个**在排队"，队列里可能同时到了多个。
ET 模式下不循环会**丢连接**（边沿只报一次）；LT 模式下是效率问题（不循环下次还报）。

**35. LT 和 ET 有什么区别？现在用哪个？为什么先用它？**
**LT**（水平触发，默认）：条件满足就**反复报**，直到你处理干净。
**ET**（边沿触发，`EPOLLET`）：**只在状态变化时报一次**，必须自己循环读到 `EAGAIN`，否则丢事件。
现在用 **LT**：容错高（漏读下次还提醒）、好调试 —— 先用它把逻辑跑通。

**36. 空闲时服务器在干什么？哪条命令能看出来？**
睡在 `epoll_wait` 里（内核态 `ep_poll`），**0% CPU**。
命令：`ps -o pid,stat,%cpu,wchan:20,cmd -p <pid>`（看 wchan）或 `cat /proc/<pid>/wchan`。

## CP6b（把分机纳入 epoll）

**37. `accept` 出来的 socket 会继承 `server_fd` 的 `O_NONBLOCK` 吗？依据？**
**不会**。`man 2 accept` 的 **VERSIONS** 一节：
> "On Linux, the new socket returned by accept() **does not inherit** file status flags such as O_NONBLOCK and O_ASYNC from the listening socket. **This behavior differs from the canonical BSD sockets implementation.**"
所以每条连接都要自己设一遍。

**38. 同一个 `EPOLLIN`，在监听 socket 和连接 socket 上含义有什么不同？**
**位是同一个位，含义由 socket 种类决定。**
- 监听 socket → **有新连接**在等 accept
- 连接 socket → **有数据可读，或者对端关闭了（EOF）**
★ 这就是 HANDOFF §8.2 标的"**真正的卡点**"。

**39. 新连接 / 有数据 / 对端发 FIN —— 三种情况的位掩码？**
**三种都是 `EPOLLIN`**（都表现为"可读"）。区别在你操作之后看到什么：
- 新连接 → `accept` 成功
- 有数据 → `read` 返回 `>0`
- FIN → `read` 返回 **`0`**

**40. `read()` 返回 0 是什么意思？为什么说"EOF 是以可读的形式通知你的"？**
`0` = **对端正常关闭**（发了 FIN），**不是错误**。
FIN 到达时内核把这条连接标成"可读"（读会立刻返回 0，不阻塞）→ 所以 epoll 报 `EPOLLIN`。
**"对端走了"这件事，是通过"可读"告诉你的。**

**41. `read()==0` 时只 `close` 就够、不用 `EPOLL_CTL_DEL`？依据？显式 DEL 有什么风险？**
依据：`man 7 epoll` ——
> "A file descriptor is removed from an interest list **only after all the file descriptors referring to the underlying open file description have been closed**."
我们没有 `dup`，所以 `close` 就等于摘干净了。
风险：如果非要"先 close 再 DEL"，中间**新连接复用了同一个 fd 号**，DEL 会删掉**新连接**的登记。
（这个"只在最后一份引用关闭后才摘除"的措辞，正是针对 `dup` 场景的警告 —— 本设计没有 dup。）

**42. 对端 RST 强断时位掩码是什么？`EPOLLERR`/`EPOLLHUP` 没订阅为什么也报？**
RST 后该 fd 变可读，`read` 返回 `-1` + **`ECONNRESET`**；位掩码常见 `EPOLLIN|EPOLLHUP`（或带 `EPOLLERR`）。
为什么没订阅也报：`man 2 epoll_ctl` 原文 ——
> EPOLLERR: "**epoll_wait(2) will always report for this event; it is not necessary to set it in events**"
> EPOLLHUP: "**epoll_wait(2) will always wait for this event; it is not necessary to set it in events**"
所以处理事件时要**主动判**这两位。

**43. 撞到 fd 上限后只 `break` 会怎样？为什么？**
**忙等死循环烧 CPU**。LT 模式下监听 fd **仍然"可读"**（队列里还有连接在等）→ `epoll_wait` 立刻又返回 → 又 accept → 又 EMFILE → 无限循环。
实测：`ulimit -n 64`，59 条连接撞墙，几秒写了 **21797 行** `accept: Too many open files`。
正确做法：EMFILE 时**把监听 fd 从 epoll 摘掉**（或不再关心它的 EPOLLIN），等有连接释放了再登记回去。**CP6d 的活**。

**44. "3 个 nc 看到 fd 5/6/7" 和 "78 条连接后 fd 还是 5" 分别说明什么？**
- 前者：**同时活着的连接拿到了三个不同号码**（"一个线程同时持有多条连接"的证据）
  ⚠ 但它**分不清"泄漏"和"正确管理"** —— 泄漏版照样打印 5/6/7，是**假绿**
- 后者：**句柄被配平**了 —— 连接关掉后号码被内核回收复用（日志里 `fd=5` 反复出现）
**两个合起来才完整**：一个证明"能同时持有"，一个证明"还回去了"。

## CP6c（ClientContext + 连接账本）

**45. `read_buffer` 为什么不能声明在事件处理的那段代码里？**
那段代码**每次事件都重新执行**，局部变量在函数返回时销毁。而"下半截请求"要等**下一次事件**（**另一次函数调用**）才拼得上 —— 跨调用活不下来。
所以必须搬进 `ClientContext`（存在 map 里，生命周期**跟着连接**，不跟着函数调用）。
★ 这**就是"状态机切片"**。

**46. `ClientContext` 为什么用 fd 当 key？事件回来时你知道什么、不知道什么？**
事件回来时你手上**只有 `events[i].data.fd`**（一个 int）。它是新连接还是老连接、对应哪条 TCP 流 —— **全是登记时你自己写进去的**。
用 fd 当 key：事件里拿到的就是 fd，**一次哈希查找**就找到状态，分流逻辑一行都不用改。
★ 替代方案 `data.ptr` 被否掉了（要引哨兵区分总机、悬垂指针会直接炸）——见 HANDOFF §7。

**47. 现在有哪两本账？各自的销账手段是什么？**
① **fd 号**（内核资源）→ 靠 **`close(fd)`** 销账；漏销的表现是 `/proc/<pid>/fd` 只涨不落
② **账本条目**（`clients` 里的 `ClientContext`）→ 靠 **`clients.erase(fd)`** 销账；漏销的表现是**内存慢涨** + 哨兵报警
★ **只 close 不 erase = 内存泄漏；只 erase 不 close = fd 泄漏。两本都得平。**

**48. 漏了 `erase` 会怎样？为什么 HTTP 测试抓不到它？** 🔥
旧条目**留在 map 里**；fd 被复用后，新连接的 `emplace` **静默失败**（没插进去）→ 那条连接**在账本里查不到** → 代码走 `continue` 跳过 → 它的数据**永远不被处理**（功能悄悄坏掉），同时 map 内存慢涨。
为什么抓不到：**fd 是平的**（close 还在），而 `p2_test.py` 跑的是"每条连接独立、马上关"的模式 —— 实测 **23/23 全过**。
→ 只有 **`emplace` 哨兵**会喊。

**49. 哨兵为什么要放在 `emplace` 那边，不能只放在 `erase` 那边？**
因为漏了 erase 之后，**旧条目还躺在账本里**；下一个连接复用同一个 fd 时，`erase` **照样能删掉它（返回 1）** —— 所以 erase 那边**永远等不到"删不到"的情况，喊不出来**。
**只有 `emplace` 这一侧才知道"这个号码不该有人占着"**（key 已存在 = 上一个没销账）。

**50. `emplace` 在 key 已存在时会怎样？`operator[]` 呢？这个差别为什么重要？**
- `emplace`：**静默不插入**，返回 `pair<iterator, bool>` —— 那个 `bool` 就是"到底插进去了没有" → **哨兵能工作的原因**
- `operator[]`：**会覆盖**（默认构造再赋值）→ 泄漏被**悄悄抹掉**，你永远发现不了
★ 差别重要在于：**"bug 能不能被发现"，取决于你选了哪个 API。**

## CP6c-2（把状态机搬进来，回真正的 HTTP）

**51. `tryHandleRequest` 的返回值不是"成功/失败"，那 `true`/`false` 各代表什么？**
**`true` = "这条连接到此为止"**（有结果了：响应发了 / 或判了死刑该丢弃）→ 调用方 `close + erase`
**`false` = "还有救，留着"**（还不够一个完整请求）→ 调用方什么都不做，`inbuf` 留着等下次事件

**52. `+4` 是什么？漏掉 `content_len` 会出什么事？** 🔥
`+4` = **`\r\n\r\n` 这 4 个字节**（`header_end` 指向第一个 `\r`，头部**内容**不含它们）。
漏 `content_len`：收满"头部+空行"就以为完整了 → **body 还没到就提前发 200**。
实测：编译器警告 `content_len set but not used`，`p2_test.py` **17/23**，6 个失败**全是"服务器提前响应了"**（t9/t11/t12）。

**53. `find` 找不到时返回什么？为什么不能拿它跟 `-1` 比？** 🔥
返回 **`std::string::npos`**，定义是 `static const size_type npos = static_cast<size_type>(-1)`；而 `size_type` 是**无符号**的 → 实际值 **18446744073709551615**（size_t 最大值）。
跟 `-1` 比：**能编译、多数情况也能work**（`-1` 会转成同一个无符号值）—— 但**语义是错的**：`npos` 不是"负数"，是"**一个不可能的下标**"。而且换个返回有符号类型的接口就崩了。
标准写法：跟 `std::string::npos` 比。

**54. "一个完整请求"的定义是哪一节给的？为什么是 `\r\n\r\n` 不是 `\n\n`？**
**RFC 9112 §2.1**（Message Format）：HTTP/1.1 行结束符是 **CRLF**；头部以一个**空行**结束 → 连着两个 CRLF。
不用 `\n\n`：① 不符合规范（**必须**接受 CRLF）② **body 里可能出现 `\n\n`**，会误判成头部结束。

**55. 头部超限时为什么返回 `true` 而不是 `false`？返回 `false` 会怎样？**
`true` = 判死刑，让调用方 `close` 掉这条连接。
返回 `false`：调用方认为"还有救"，**留着连接继续等** → 对方继续灌数据 → **`inbuf` 一直涨 → 内存爆掉**。
这正是 `MAX_HEADER_SIZE` 要防的 DoS。

**56. "不够一个完整请求就 `return false`"这一行，为什么它就是"状态机切片"？**
因为它把"**等着收全**"从"**堵在函数里**"改成了"**退出函数、把进度留在 `ctx.inbuf` 里**"。
对比 `p2.cpp`：那边是 `while (read_buffer.size() < total) { read... }` —— 函数**不返回**，进度在**栈上**的局部变量里。
这边**返回**，进度在**堆上**的 `ClientContext` 里；下次事件**重新进函数**、**重头算一遍 `total`**。
"切片" = 一个连续执行的过程，被切成"**每次事件恢复一点进度**"。

**57. 三段纯函数搬过去为什么一行不用改？"纯"在这里指什么？**
"纯"（pure function）= **不依赖全局变量、不做 IO**，输入相同输出就相同。
所以它们只依赖自己的参数，跟"在哪个文件、有没有 socket"**完全无关** → 复制过去就能用。
实测：`toLowerAscii` / `findHeader` / `isAllDigits` 在两个文件里的**代码部分逐字节相同**。
★ 这也是"为什么搬家这么省事"的答案：**纯函数搬家不要钱。**

**58. `ClientContext& ctx = it->second;` 里那个 `&` 去掉会怎样？为什么这类 bug 特别难查？**
去掉就变成**拷贝一份**，改的是副本 → `inbuf` 攒的东西**全丢**，服务器表现为"**永远收不全请求**"。
难查的原因：**它能编译、能运行、不崩溃、零警告** —— 只是**静默地什么都不做**。
和 `for (char c : out)` 少一个 `&` 是**同一类 bug**，只能靠**理解语义**发现，工具帮不上忙。

**59. 为什么 [1][2][3] 自动失效，而 [fd 配平] 没有？**
[1][2][3] 测的是 **echo 契约**（"发什么回什么"）—— CP6c-2 把契约换成了 **HTTP**，这三个用例的**前提没了**，所以自动失效（**不是代码坏了**）。
[fd 配平] 测的是"**句柄有没有还回去**"，它**不关心服务器回什么** → 与协议**正交**，所以跨两次重构依然成立。
★ 教训：**测"行为契约"的用例会随需求变；测"资源不变量"的用例能活很久。**

**60. `EMFILE` 和 `ENFILE` 分别是什么？为什么 `ulimit -n` 撞出来的是前者？** 🔥
`man 2 accept` 里这两条**挨着**，意思完全不同：
· `EMFILE` = **本进程**的 fd 用光了（The **per-process** limit ... has been reached）
· `ENFILE` = **整机**所有进程加起来用光了（The **system-wide** limit ... has been reached）
`ulimit -n` 改的是**这个进程**的上限 → 撞出来的是 `EMFILE`。
测试里那句 `bash -c 'ulimit -n 64; exec ./epoll'` 压的就是这个数。
★ 填错的代价：暂停分支**永远进不去** → 空转照旧（实测日志 **109 万行**）。

**61. 撞到 `EMFILE` 后为什么不能只是 `break`？** 🔥
`break` 只退出了 `accept` 循环，**`server_fd` 还登记在 epoll 里**。
而 accept 队列里还排着没被接走的连接 → 在 **LT 模式**下它**依然"可读"** →
`epoll_wait` 立刻返回 → 又进 `accept` → 又 `EMFILE` → 又 `break`……
**中间没有任何等待，因为条件永远成立。**
实测：2 秒 **+1,098,114 行**日志、CPU **75%**、**连已经连上的用户都超时**。

**62. 把 `server_fd` 从 epoll 摘掉，为什么就能止住空转？**
`epoll_wait` 只报告**登记在 interest list 里**的 fd。摘掉之后内核**根本不会通知**它 →
这一轮 `epoll_wait` 没它的事 → **线程真的睡下去**（`ep_poll`，0% CPU）。
摘掉之后它在等的只剩**分机上的事件**（数据到达 / 对端关闭）—— 而这些正是"腾出 fd"的来源。

**63. 恢复判断为什么必须在循环**里面**？为什么放 `epoll_wait` 之前？** 🔥
**先说被推翻的那半句**：代码注释原来写"必须放在 `epoll_wait` 之前，放循环体末尾会
`暂停 → 恢复 → 再暂停` 又变死循环" —— **实测不成立**：

| 变体 | [1] 不空转 | [2] 能恢复 |
| --- | --- | --- |
| 放 `epoll_wait` **之前**（现在） | PASS | PASS |
| 放 `while` 体**末尾** | PASS | **PASS**（注释说会死循环 —— 不会） |
| 放 `while` **外面** | PASS | **FAIL：连不上** |

**真正硬性的只有一条：必须在循环里面。** 放外面 = 这段永远不执行 →
摘了话筒再也放不回去（`[2]` 抓得到，`[1]` 照样绿）。
两个可行位置其实**等价**：`N+1` 轮的"`epoll_wait` 之前"和 `N` 轮的"循环体末尾"之间没有别的事发生。
★ 留在这里只是因为语义清楚：**"能不能恢复"是【睡前】要问的问题 —— 先问，再睡。**
★ 更值钱的教训：**注释里写的原因，也可能是没验证过的猜测。** 这已经是这个项目里第二次了。

**64. `paused_at` 为什么必须记"暂停那一刻的 `clients.size()`"？填 `0` 会出什么事？** 🔥
因为恢复判据写的是 `clients.size() < paused_at` —— **两个是一对契约，改一个另一个就废**。
填 `0`：`size()` 返回 **`size_t`（无符号）** → `0 < 0` **永远不成立** → 恢复分支永远进不去 →
**话筒摘了就再也放不回去**（服务器变聋）。
实测：`[2] FAIL 连不上：timed out`，而 `[1]` **照样绿**（因为它只测"不空转"）。
★ 所以 `emfile_test` 必须有**两个**用例 —— 只跑 `[1]` 是发现不了这个 bug 的。

**65. `ctx.inbuf.erase(0, total)` 不写会怎样？为什么表现是"同一个请求被回了两遍"？**
不删的话，`inbuf` 开头**永远**是那个已经处理过的请求 →
下次事件进来 `find("\r\n\r\n")` **又找到它** → 再回一遍 → 再 `return true` → 调用方再循环……
**排在它后面的请求永远轮不到**（服务器卡在第一个请求上）。
★ 这就是"消费"（consume）的含义：处理掉多少字节，就从缓冲区**头部**删掉多少。

**66. `bool want_close = true;` 和 `ctx.want_close = true;` 差在哪？为什么编译器只给 warning？**
**看行首有没有类型**：
· `bool want_close = true;` —— 行首有 `bool` = **声明**，**新建一个局部变量**，跟 `ctx` 毫无关系
· `ctx.want_close = true;` —— 没有类型 = **赋值**，改的才是 `ctx` 里的成员
实测 A/B：前者写完 `ctx.want_close` 还是 `0`；后者才是 `1`。
只给 **warning**（`unused variable`）因为"声明一个没用过的变量"是**合法语句**，不是语法错误。
★ **对警告不能当噪音** —— 它几乎总在说"你这行没起到你想的作用"。

**67. 读 `Connection` 头的代码，为什么不能照抄读 `Content-Length` 那一整段？** 🔥
两者**只有前半截像**（都是 `findHeader` 取值交给一个值变量），**后半截完全不同**：
· `Content-Length` 的后半截是 `isAllDigits` → `stoull` → 比 `MAX_BODY_SIZE` —— 在做"**把数字串转成整数**"
· `Connection` 的值是 `"close"` / `"keep-alive"` —— **只要比字符串**
照抄的后果：`isAllDigits("close")` 永远为假 → 每个带 `Connection` 头的请求都被判"非法"丢弃 →
**连响应都不发**。实测日志刷 **109 万行** `Connection 非法（不是纯数字）`。
★ 更阴的：那段里还有一行 `content_len = static_cast<size_t>(v);` ——
如果客户端发 `Connection: 5`，它会走到这行，**把真正的 `Content-Length` 覆盖掉**。
**抄错的代价不只是"没生效"，还会污染别处的数据。**
★ 教训：**"照抄形状"可以，但抄进来的每一行都得知道在干嘛。**

**68. 一条连接上来了两个请求，`tryHandleRequest` 为什么要被循环调用？**
因为它一次只处理**一个**请求（处理完 `return true`，同时 `erase` 掉那一段）。
一次 `read` 可能把**两个请求一起**收进来（粘包）→ `inbuf` 里同时躺着两个 →
只调一次的话，第二个就**永远躺在 `inbuf` 里没人管**（不会再有任何事件来叫醒它）。
所以：`while (tryHandleRequest(ctx)) { ... }` —— 一直问到它说"不够一个完整请求"（`false`）为止。

**69. 现在服务器靠什么"规避"粘包？代价是什么？**
⚠ 这题的问法基于**旧状态**（CP6d-2 之前）：那时每个响应都写死 `Connection: close`，
回完就关 → **一个连接只会被处理一个请求** → "粘包"问题被绕过去了。
代价：① 每条连接只能服务一个请求 → 浏览器拿 14 个资源要握 14 次手（实测 200 个请求留下
**402 个 `TIME_WAIT`**）② 与 HTTP/1.1 的默认行为（复用）不符。
**CP6d-2 之后这个问题不再"规避"而是正面解决了**：`want_close` + `inbuf.erase` + 循环解析。
